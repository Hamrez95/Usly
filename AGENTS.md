# Usly engineering guide

## Product boundary

Usly is a privacy-first shared-experience planner for couples. It is not therapy,
diagnosis, surveillance, a relationship score, or a chat product. Raw private
answers must never be revealed to the partner, analytics, logs, or push copy.

## Repository flow

- `main` contains verified stable releases only.
- `dev` is the version-batch integration branch.
- Use short-lived `feat/`, `fix/`, or `chore/` branches and pull requests.
- Do not commit secrets, generated APK/AAB/ZIP files, or `.env`.

## Mobile checks

Run from `apps/mobile`:

```bash
flutter pub get
dart format --set-exit-if-changed lib test
flutter analyze
flutter test
flutter build apk --release
```

The Android runner is currently generated by CI until it is checked in. Do not
claim reproducible release status until the runner and lockfile are committed.

## Build entry point

From the repository root on PowerShell:

```powershell
./scripts/build-app.ps1 -Target android-apk -Configuration Release
./scripts/build-app.ps1 -Target android-aab -Configuration Release
```

Artifacts and SHA-256 metadata are placed under `artifacts/<version>/`.

## Supabase safety

- Flutter may contain only the project URL and publishable/anon client key.
- Never ship `service_role` or a secret key.
- Enable RLS for every exposed table and test cross-couple access.
- Private response tables are owner-readable only; shared state must be derived.
- Do not apply `supabase/schemas/usly_alpha.sql` to a project until its exact
  project ID is verified and the draft is converted into a CLI-generated
  migration after advisor review.
